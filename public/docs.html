Architecture

The camera process owns the synthetic RTSP source, Server A owns video processing and delivery, and Server B owns user authentication, browser commands, and session state.

          ▼
  MediaMTX at rtsp://127.0.0.1:1111/camera
          │ RTSP consume
          ▼

  FFmpeg stream copy → rolling HLS files
          │                           ▲

Camera flow

FFmpeg generates a changing test pattern and publishes H.264 to MediaMTX. Both child processes are supervised and automatically restarted after unexpected exits.

Video flow

Server A's FFmpeg reads MediaMTX over RTSP/TCP and stream-copies H.264 into approximately one-second MPEG-TS HLS segments. hls.js requests the playlist and every segment with a Bearer JWT.

Authentication flow

The browser posts credentials to Server B. Server B verifies a bcrypt password hash, creates an in-memory session, signs a one-hour JWT, and synchronizes the session to Server A.

Control and authorization

The browser sends commands over an authenticated WebSocket. Server B forwards video commands over its persistent Server A socket; that same connection carries full session snapshots, activations, and revocations.

Bonus A: role-based access control

Server B—not the browser—enforces command permissions from the role already verified against the active session. Unknown roles fail closed for control commands.

A forbidden command is logged, receives a correlated Forbidden response, and does not close the viewer's WebSocket or reach Server A. The admin account uses the existing operator role.

Setup instructions

Prerequisites

  • Node.js LTS and npm
  • FFmpeg with H.264 encoding support
  • MediaMTX

Install and configure

npm install
cp .env.example .env
npm run create-users

Edit .env with strong, different JWT_SECRET, INTERNAL_WS_SECRET, and LOG_HMAC_SECRET values. Set FFMPEG_PATH and MEDIAMTX_PATH to executable names on PATH or full platform-appropriate paths. Keep WEB_ORIGIN aligned with the Server B browser origin.

Verify the command log

npm run verify:command-log

Run in three terminals

npm run start:camera
npm run start:server-a
npm run start:server-b

Then open http://127.0.0.1:3002/. On Windows 11 x64, install native x64 FFmpeg and MediaMTX distributions and configure their executable paths in .env; application code does not assume a filename suffix or Unix directory layout.

Security bonus

HMAC command-log integrity

Every protected NDJSON record contains previousHash and hash. The first uses GENESIS; every later record links to its predecessor. The HMAC-SHA256 input is deterministic JSON ordered as timestamp, user, message, requestId, status, error, and previousHash, with absent optional values represented as null.

Server B verifies every existing entry before it starts listening and serializes each compute-and-append operation. Corruption aborts startup. If an audit append fails while handling a command, the request stops and an unlogged management action is not forwarded. The legacy development log is archived as commands.pre-hmac.log and is not claimed to be protected.

Architectural decisions

  • WebSocket between servers: satisfies the non-REST requirement, carries correlated commands and session events, and reconnects automatically.
  • HLS delivery: is browser-compatible and operationally straightforward; hls.js makes authenticated cross-origin media requests possible.
  • H.264 stream copy: avoids a second encode, reducing CPU usage and delay.
  • One-second segments: balance latency, request overhead, and reliable playback. hls.js targets roughly two segments behind live.
  • Global videoRunning state: the assignment defines one camera and global START/STOP commands, so one in-memory delivery flag is sufficient.
  • STOP as a delivery gate: returns HTTP 503 for authorized HLS requests while the camera, RTSP source, FFmpeg, and segment generation continue unchanged.
  • JWT plus jti: the signature proves token integrity; the synchronized session identifier enables immediate per-session logout.
  • Independent Server A validation: Server A verifies JWT cryptography and local active-session state without a REST dependency on Server B.
  • Fail closed: Server A returns HTTP 503 when session state is not synchronized, preferring revocation safety over video availability.
  • In-memory sessions: keep the mandatory prototype small; restarting Server B intentionally invalidates all sessions.
  • Cross-platform spawning: executable paths are configurable and child processes use argument arrays with shell: false.
  • No C++: no mandatory requirement needs a native addon; C++ belongs only to an optional bonus and is not used.

Specification ambiguities and chosen interpretations

  • “Stop video” is interpreted as stopping delivery, not stopping production, because the source and related processes must continue running.
  • Authorization must support immediate logout, so JWT verification is combined with synchronized active-session state rather than signature validation alone.
  • The video state is global because only one camera and no per-user stream state are specified.
  • The mandatory assignment defines roles but no permission matrix. Bonus A supplies the explicit viewer/operator command matrix while preserving video access for both.
  • A changing test-pattern counter satisfies the requirement for visible motion/time without relying on an optional FFmpeg text filter.

Limitations

  • Typical local HLS latency is approximately 2–4 seconds, with about 3 seconds expected.
  • Sessions and the global video state are in memory; restarting Server B invalidates existing sessions.
  • Operators control one global stream; there is no per-camera or per-user video state.
  • Both servers share an HS256 JWT signing secret and an internal WebSocket service secret.
  • The local prototype uses HTTP and WebSocket without TLS.
  • There are no refresh tokens or persistent database.
  • The browser WebSocket authenticates with a JWT query parameter because browser WebSocket APIs cannot set an Authorization header.
  • commands.log has no rotation. HMAC chaining detects record modification, middle deletion, and reordering, but does not prevent tampering.
  • An attacker who also obtains LOG_HMAC_SECRET can recalculate the chain. Complete-file deletion cannot be cryptographically detected without an external trusted checkpoint; production should use centralized append-only/auditable storage.
  • Asymmetric encryption, C++/N-API, and TPM integration are not implemented.
  • Windows 11 x64 compatibility is designed and source-reviewed, but runtime validation was performed on macOS Apple Silicon and remains pending on Windows.
